KASUGAI Canvas v7.1.0

データ形式（推奨） — WEB 化の変換先と採用ルール

1. 推奨データ形式

既存の GIS データを KASUGAI Canvas 向けに WEB 化する際の変換先の定石と、形式を採用する際のルールをまとめたページです。個別形式の仕様は データ形式（標準）・データ形式（オプション・エンジン別） を参照してください。

1.1 2D/3D 追従表示の基本データ形式（方針・未実装）

ズーム追従ルート（方針）のデータ形式切替図 — 広域は XYZ ラスタ、拡大は FlatGeobuf。3D は同じ 2 段に 3D Tiles が並走します。広域ではラスタ化された見た目で軽量に表示し、拡大して地物単位の解像度が必要になったらベクター読み込みへ切り替えます。広域側はベクターの全件・大量読み込みを回避する「負荷逃がし」が目的であり、FGB の bbox=auto だけでも動く現行経路への上乗せです。

これは未実装の方針メモです。カメラ追従（QGIS ライブ連携の ?follow/live: 行のフォロー・Fly 再生等）でズームに応じてデータ経路を切り替える設計の前提として、ここに方針だけを明示します。現行実装では flatgeobuf:（bbox=auto）が全ズームで範囲読みする単一経路であり、以下の 2 段構成の切替機構はまだ存在しません。
  • 切替閾値はズーム帯で設ける — ハードな境界だとラスタ→ベクターの見た目が飛ぶため、境界±1ズーム程度のオーバーラップ（FGB 読み込み完了まで XYZ を残す）を想定
  • 広域側はラスタのみ — ピック・属性パネル・ベクター検索・選択ハイライトは拡大側（FGB）でのみ有効。追従ミラー用途では許容とする
  • 広域ラスタの生成元は未定 — 既存の /live/render（QGIS 描画の透過 PNG・moveend 追従）流用が実装最小、事前タイル化した xyz: ツリーも可。QGIS 側 OGC 配信（WMS/WMTS）は撤去済みのため復活させない
  • 3D は同じ 2 段＋ 3dtiles: — 広域 XYZ はイメージレイヤー（地球面ドレープ）、拡大 FGB は entity/primitive 描画。3D モデル・点群はタイル自身の LOD が縮尺を吸収するため切替不要
  • 追従ポーリングとの整合 — /live/state 1.5s ポーリング → moveend デバウンス（現行 400〜700ms）再クエリで現行機構のまま成立。連続ズーム操作時の追いつき遅延は実装時に実機確認

1.2 WEBVIEW連携（geo_webview エクスポートのベクター出力形式）

WEBVIEW連携（QGIS → Canvas の出力）：QGIS プラグイン geo_webview の .kasc+canvas_data/ エクスポートにはベクター出力形式スイッチがあり、「ネイティブ（そのまま参照）」（native・既定） は読めるソースを gpkg:/geojson:/flatgeobuf:/geoparquet:/duckdb: 等の行でそのまま参照し（ネイティブ参照できないベクターは recommended と同じ FlatGeobuf 変換経路）、「推奨（FlatGeobuf → canvas_data/）」（recommended） は全ベクターを本ページ第一推奨の FlatGeobuf（EPSG:4326・空間インデックス付き）へ変換して canvas_data/ へ flatgeobuf: 行として配置します。ソース別の行タイプ対応は .kasc 行の生成規則、連携全体は QGIS・GDAL 連携 を参照してください。

第3のモードとして 「WEB連携（GeoJSON → canvas_data/）」（geojson） があります。これは FGB/GeoParquet を含む全ベクターを GeoJSON に変換して canvas_data/ へ geojson: 行として配置する出力で、生成物がオープン標準の GeoJSON のみになるため、KASUGAI Canvas 以外の WebGIS や GIS ツールでも canvas_data/ をそのまま読み込めます。広域配信や読み込み性能は FlatGeobuf に劣るため、Canvas 専用配信では recommended、他 WebGIS との相互運用を優先する場合は geojson を使い分けます。

結論: ベクター = FlatGeobuf（flatgeobuf:）、大規模な属性・SQL 絞り込み = GeoParquet + duckdb:、ラスタ・オルソ = XYZ タイル（base:/xyz:）、3D = 3D Tiles（3dtiles:）

1.3 採用ルール

青のノードが推奨形式（推奨 バッジの形式）、グレーのノードは変換不要でそのまま使える経路です。分岐条件の詳細:

  • FlatGeobuf は空間インデックス付きで書き出すこと（GDAL は既定で付与）。bbox=auto 既定 ON で空間インデックス+HTTP Range の範囲読み・重いランタイム不要・全4エンジン対応
  • GeoParquet + duckdb: は述語プッシュダウン・row group スキップ・列プルーニングで「必要な列と範囲だけ」読む。検索は常に全件対象。DuckDB-WASM 約60MB の初期ロードあり（SW 永続キャッシュで初回のみ）
  • geoparquet: 直接経路 は全件読み込みだがバイナリで軽量・変換不要で置くだけ。超大規模は duckdb: 経路へ
  • XYZ タイル はネイティブ・全エンジン・プログレッシブ表示。ドローンオルソ等もタイル化して配信するのが定石

1.4 採用しない方がよい形式（WEB 配信の変換先として）

  • GeoPackage → gpkg: 直配信 — sql.js がファイル全件を WASM メモリへ読み込み、大規模では実用速度にならない。管理用マスターとして保持し、配信用は FlatGeobuf/GeoParquet に変換
  • MVT / PMTiles — ネイティブ動作は MapLibre と Navara のみ。4エンジン共通の変換先にはならない（オプション扱い）
  • GeoTIFF / COG 直配信 — Cesium 限定のオプション経路。汎用 WEB 配信では XYZ タイル化を推奨
  • 大規模データの GeoJSON 化 — テキスト解析が重く転送量も大きい。数万地物以上はバイナリ形式へ

1.5 推奨形式の詳細

🧭 FlatGeobuf 推奨

flatgeobuf: / fgb:。ベクターの第一推奨。bbox=auto（既定 ON）で空間インデックス＋HTTP Range による表示範囲のみの部分読み込み。カメラ移動で自動再クエリ。索引なし・Range 非対応サーバーは全件読み込みへフォールバック。bbox=off で全件読み込み系（ベクター検索対象）に戻る。where= 対応。

📦 GeoParquet + duckdb: 推奨

duckdb: で GeoParquet/Parquet を指定。超大規模・属性絞り込みの第一推奨。述語プッシュダウン・row group スキップ・列プルーニング・bbox=auto で「見ている範囲だけ読む」。検索は常に全件。DuckDB-WASM は約60MB・SW 永続キャッシュで初回のみ。

📦 GeoParquet 推奨

geoparquet: / parquet:。中規模ベクターをクエリなしで置くだけ配信する場合の推奨。軽量デコーダー（hyparquet）で全件読み込み → GeoJSON 正規化。範囲読み込みは duckdb: 経路。

🗺️ XYZ タイル 推奨

base: / xyz: / tile:。ラスタ・オルソの第一推奨。全エンジンでネイティブ描画・プログレッシブ表示。タイル化済みオルソ（地理院 seamlessphoto 等）はそのまま、ドローンオルソ等の GeoTIFF はタイル化して配信。

🏙️ 3D Tiles 推奨

3dtiles:。3D データの標準変換先。Cesium はネイティブ、MapLibre/OpenLayers/Leaflet は deck.gl 経由で描画。点群（EPT/LAZ 等）・3D モデル・建物データはすべて 3D Tiles 化して配信。

1.6 前提条件（採用時の確認事項）

  • FlatGeobuf は空間インデックス必須 — ogr2ogr -f FlatGeobuf（GDAL）は既定で空間インデックスを書き込む。索引なしファイルは範囲読み不可で全件転送になる
  • Range リクエスト対応ホストを選ぶ — FlatGeobuf/PMTiles/COG/duckdb: の効果は HTTP Range 対応（GitHub Pages・S3・CloudFront・ローカル Rust サーバー等）が前提。非対応だと全量ダウンロードにフォールバック
  • 空間ソートを推奨 — GeoParquet/FlatGeobuf を書き出す前に地域順・ヒルベルト的な並びにすると、範囲読み込みの局所性が上がる
  • GeoPackage は配信形式ではなく管理形式 — 配信用には必ず変換する

1.7 変換方法の例

# ベクター → FlatGeobuf（空間インデックスは既定で付与）
ogr2ogr -f FlatGeobuf out.fgb in.gpkg layer_name

# ベクター → GeoParquet
ogr2ogr -f Parquet out.parquet in.gpkg layer_name

# ラスタ・オルソ → XYZ タイル
gdal2tiles.py -z 5-18 in.tif tiles/
