QGIS・GDAL連携

本章では、KASUGAI Canvasをメイン画面・最終2D/3D表示エンジンとし、QGIS・GDALを多様なGISデータを扱うための変換・編集・解析基盤として連携する構成をまとめる。

QGIS→KASUGAI の送出は実装済みです。QGIS プラグイン geo_webview （qgis_live_harness）が レイヤーツリーを .kasc + DATA/ としてエクスポートし、「▶ Canvas」でローカルアプリへ外部プロジェクト登録、 または静的ホストへ配信して ブラウザ WebGIS（?kasc=）で再生できます。 実装済みの再現範囲（レイヤー行対応表・スタイル引継ぎ・起動経路・未対応 Issue）は QGIS・GDAL連携 — 実装済みの再現範囲、 描画性能とデータ形式の既定は 描画性能とデータ形式の整備方針 を参照。

基本方針

QGISの画面やQgsMapCanvasをKASUGAIへそのまま埋め込むのではない。QGIS・GDALが扱える多様な入力形式を、KASUGAI Canvas（CesiumJS）が描画できる形式へ変換・配信する。

エクスポート出力物（out_dir）の構成：

  • out_dir/出力先の優先順：設定 kasugai_output_path ＞ <Canvasインストール>/QGIS_projects/<project-slug>/ ＞ <ドキュメント>/kasugai_canvas_qgis
    • kasugai_canvas.kasc固定名。レイヤー行＋cam:/theme:/bookmark: 行
    • bookmarks.xmlqgis_bookmarks 形式（0件時は出力しない）
    • [opt] <engine>.html + index.htmlemit_launchers 時：cesium/maplibre/openlayers/leaflet/gsimaps の起動ページ＋案内ページ（index.html から ZIP もDL可）
    • DATA/
      • <slug>.qmlレイヤースタイル（saveNamedStyle）
      • <slug>__<theme>.qmlテーマ別スタイル（テーマ記録の名前付きスタイル。theme: 行の ;style= が参照・v4.6.0〜）
      • <slug>.<ext>ローカルデータ複製（.gpkg/.geojson/.fgb/.parquet）＋変換GeoJSON（EPSG:4326）
      • <slug>/XYZ タイルツリー / 3D Tiles tileset（サイズ上限 1GiB）
      • <slug>_<asset>.svg/png.qml が参照するシンボル画像

ZIP（kasugai_canvas_<ch>.zip）は別枠： パネルの ZIP ボタン・index.html のDLリンクは /export-data/kasugai_canvas_<ch>.zip がその場で固めて返す方式で、 out_dir にはファイルを残さない（常に直近エクスポートの最新内容）。 emit_zip=True（bridge/API 経路）を指定した場合のみ out_dir に ZIP が出力される。 この ZIP は Re:Earth geo_suite の qgis: 行が URL で直接取り込める。

命名ルール（slug で .kasc 行・データ・スタイルが紐付く）：レイヤー名 → _slugify() で英数・_- 以外を _ に置換（日本語名は layer＋連番にフォールバック、衝突時 _2…）。.kasc のレイヤー行は geojson: タイトル | DATA/<slug>.geojson | on | style=DATA/<slug>.qml の形で同じ slug を参照するため、行・データ・.qml の3者はファイル名で対応する。.kasc ファイル名は固定の kasugai_canvas.kasc、プロジェクト名は Canvas インストール先の QGIS_projects/<project-slug>/ ディレクトリ名に使われる。

データの3層構造

編集用データと描画用データを同じ形式に統一しない。正データ、配信用データ、描画データを分離する。

正データ
GeoPackage / PostGIS / FileGDB / GeoTIFF
        ↓ 変換・抽出・タイル化
配信用データ
GeoJSON / GeoParquet / FlatGeobuf / XYZ / WMTS / 3D Tiles
        ↓ 読み込み・ブラウザ内デコード
描画データ
GeoJSON → GeoJsonDataSource（entity）/ GeoJsonPrimitive
層 目的 主な形式
正データ 編集、属性、解析、保存 GeoPackage、PostGIS、FileGDB、GeoTIFF
配信用データ 範囲・ズーム単位の取得 GeoJSON、GeoParquet、FlatGeobuf、XYZ、WMTS、3D Tiles、MVT/PMTiles（MapLibre エンジン）
描画データ GPUへ効率よく渡す GeoJSON → GeoJsonDataSource（entity）/ GeoJsonPrimitive（バッチ描画）

この分離により、編集に適した形式を維持しながら、表示には高速な別形式を利用できる。

ベクター連携：QGIS・GDALからKASUGAI Canvasへ

ベクターは、QGIS・GDALを正データへのアクセスと変換の窓口にする。

GeoPackage / FileGDB / PostGIS
        ↓
QGIS Processing / GDAL・OGR
        ↓
┌────────────────────────────────────┐
│ 小規模・編集結果       → GeoJSON    │
│ 中規模・置くだけ       → GeoParquet │
│                        / FlatGeobuf│
│ 大規模・絞り込み       → duckdb:/sql:│
│ 広域・範囲配信         → MVT(将来)  │
└────────────────────────────────────┘
        ↓
GeoJSON 正規化 → GeoJsonDataSource / GeoJsonPrimitive

GeoJSON：最初の連携形式

小〜中規模データ、編集直後の確認、属性連携に使用する。現在のKASUGAI Canvasはgeojson: 行タイプを GeoJsonDataSource で描画するため、最初のQGIS連携形式に適している。

QGIS / GDAL
    ↓ GeoJSON
KASUGAI `geojson:` → `GeoJsonDataSource`

実装済み: QGIS→KASUGAI 送出(geo_webview)：QGIS プラグイン geo_webview の「KASUGAI」ボタン / GET /kasugai エンドポイント / bridge の kasugaiExport で、レイヤーツリーを .kasc+DATA/(スタイル .qml 同梱) として出力し、起動中の KASUGAI へ外部プロジェクト登録・切替まで行える。 GPKG/GeoParquet/FlatGeobuf ソースは変換せずネイティブ参照し、それ以外のベクターは GeoJSON(EPSG:4326)へ変換する。KASUGAI 側は web プラグイン qgis-import (プラグインカタログ)の「QGISから取り込み」ボタンからも同エンドポイントを呼べる。

MVT：大規模ベクターの将来形式

広域・大容量データでは、全件をGeoJSONで取得せず、表示範囲とズームに応じてMVTを取得する。

KASUGAIの表示範囲・ズーム
        ↓
MVTタイル取得
        ↓
MVTデコード → GeoJSON 正規化 or 専用タイル描画（将来検討）
        ↓
必要に応じて地形・3D Tilesへドレープ

MVTの生成・配信には、QGIS Server、GDAL・OGR、データベース側のタイル生成、専用のタイル生成処理を利用する。タイルの読み込みは MapLibre エンジンで実装済み（mvt:/pmtiles: 行。layers= でソースレイヤ指定。PMTiles は単一ファイル＋Range リクエストで静的ホストにそのまま置ける）。Cesium エンジンの MVT 経路と、QGIS→タイル生成の自動出力は未実装であり、後述の整備方針に従って進める。なお現行でも duckdb: の bbox=auto により「表示範囲だけ読む」運用はParquet系で実現できる。

GeoParquet・FlatGeobuf：大容量ローカルデータ

ローカルPC上で大容量ベクターを高速に扱う場合は、列指向・空間インデックス付きのバイナリ形式で出力し、ブラウザ内デコードしてGeoJSON正規化経路へ渡す。いずれも実装済み。

QGIS / GDAL
    ↓ GeoParquet / FlatGeobuf 出力
geoparquet: / flatgeobuf:（全件読み込み）
    または duckdb: / sql:（SQL絞り込み・bbox=auto）
    ↓ ブラウザ内デコード（hyparquet / flatgeobuf / DuckDB-WASM）
GeoJSON
    ↓
GeoJsonDataSource / GeoJsonPrimitive

これらのバイナリ形式はすべてのデータの標準形式にするのではなく、GeoJSONで十分な小規模データや、SQL絞り込みが適する大規模データとは使い分ける。

ラスタ連携：公開サービスとQGIS管理データ

公開XYZ・WMTS

公開されているXYZやWMTSは、QGISとKASUGAIが同じ配信元をそれぞれ直接利用する。

公開XYZ / WMTS
    ├─ QGISで読み込む
    └─ KASUGAIで直接読み込む

この場合、QGISがKASUGAIへ再配信する必要はない。

QGIS管理ラスタ

QGIS Desktopは既存のXYZを読み込めるが、QGISプロジェクト内のGeoTIFF等を自動的にXYZとして配信するわけではない。QGIS管理ラスタをKASUGAIへ渡す場合は、次のいずれかを選択する。

QGIS管理ラスタ
    ├─ QGIS Server → WMS / WMTS
    ├─ 事前タイル化 → XYZ
    ├─ COG / 独自タイル配信
    └─ ローカルファイルをKASUGAIが直接取得

WMTSをKASUGAIで利用する場合は、CesiumJS の WebMapTileServiceImageryProvider で読み込めるが、TileMatrixSet、座標系、原点、ズーム番号、Y軸方向がXYZ形式と一致するか確認する。一致しない場合は、Rust/Axum等のタイルアダプターでXYZリクエストをWMTSへ変換する。

DEM・3Dデータ：KASUGAIで直接描画

DEMと3D都市モデルは、可能な限りQGISを経由せず、KASUGAIが直接ストリーミングする。

DEM標高タイル
    ↓
KASUGAI `TerrainProvider`（地理院標高PNGデコード実装済み）

3D Tiles
    ↓
KASUGAI `3dtiles:` → `Cesium3DTileset`

QGISベクター
    ↓ GeoJSON / GeoParquet / FlatGeobuf / duckdb:/sql:
GeoJSON 正規化 → `GeoJsonDataSource` / `GeoJsonPrimitive`
    ↓
CLAMP_TO_GROUND / ドレープ設定
    ↓
DEMまたは3D Tilesの表面へドレープ

QGISとKASUGAIが同じ3Dデータソースを参照できればよく、同じ描画処理を共有する必要はない。

  • QGIS：参照、属性、管理、解析
  • KASUGAI：Terrain、3D Tiles、点群、3DGSの最終描画

高さ基準はデータごとに管理する。標高とWGS84楕円体高が異なるデータを重ねる場合は、QGIS処理層またはKASUGAI側で補正する。

カメラ・CRS・連携状態

カメラの正本はKASUGAI Canvasとする。KASUGAIの表示範囲や選択位置を、必要に応じてQGIS処理層へ通知する。

KASUGAI cameraState
├─ longitude
├─ latitude
├─ zoom
├─ bearing
└─ pitch
        ↓ 必要に応じて
QGIS処理層へ中心座標・範囲を通知

pitch は Cesium の camera.pitch と同じ符号（水平 0°、真上 +90°、真下 −90°）を採用します。

QGISプロジェクトのCRSからKASUGAIの表示用座標系へ変換する。通常のWeb表示ではWGS84経度緯度を基本とし、編集・解析時は元レイヤーのCRSを維持する。

現行実装と構想の境界

現行のKASUGAI Canvasで利用できる主な形式と、今後の構想を分けて管理する。

現行
QGIS相当のデータ → GeoJSON → geojson: → GeoJsonDataSource
                → GeoParquet → geoparquet: / duckdb:
                → FlatGeobuf → flatgeobuf: / duckdb:(format=read・要 spatial)
                → GPKG      → gpkg:（sql.js Worker・実装済み）/ duckdb: format=gpkg
                → Shapefile等 → duckdb: format=read（ST_Read・非 COI 環境では不可）
DEM               → TerrainProvider（地理院標高PNG対応）
3D Tiles          → 3dtiles: → Cesium3DTileset
XYZ               → xyz: → ImageryLayer
ベクタータイル    → mvt: / pmtiles:（MapLibreエンジンのみ・layers= 指定）

構想
QGIS / GDAL
    ├─ 広域・範囲配信 → PMTiles/MVT 生成＋Cesium側タイル経路（将来）
    └─ 編集・解析     → PyQGIS / GDAL連携API

MVT経路、QGIS Processing、PyQGIS、GDAL連携APIは、現行実装に追加する拡張機能である。

大規模データの描画性能とデータ形式の既定方針（QGIS との速度比較・実行環境別の特性・規模別の既定形式・整備課題）は 描画性能とデータ形式の整備方針 に分離して管理する。

設計上の結論

本構想の基本方針は、次のとおりである。

KASUGAI Canvasをメイン画面および最終2D/3D表示エンジンとし、QGIS・GDALを多様なGISデータをCesiumJSが描画できる形式へ変換・配信する基盤として利用する。

QGISの画面をKASUGAIへそのまま埋め込むのではなく、正データを維持したまま、用途に応じてGeoJSON、GeoParquet、FlatGeobuf、XYZ、WMTS、3D Tiles等へ変換する。小規模データはGeoJSON、中規模はFlatGeobuf（既定化を推進）、大規模・広域はPMTiles/MVT（MapLibre エンジン実装済み）とduckdb:/sql:の併用を基本とし、KASUGAIのCesiumJSとThree.jsで最終描画する。
