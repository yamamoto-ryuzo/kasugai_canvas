KASUGAI Canvas v6.23.0

描画性能とデータ形式の整備方針 — QGIS との速度比較・実行環境別の特性・規模別の既定形式と整備課題

概要

QGIS と KASUGAI Canvas の連携において「大量データを高速に処理できるか」は データ形式と読み出し方式で決まる。本ページは、QGIS 本体と WebGL ベースの Canvas をシステムとして速度比較した結果と、それに基づくデータ形式の既定方針・整備課題をまとめる。 形式の一覧・詳細仕様は データ形式、QGIS 側の連携仕様は QGIS・GDAL連携 を参照。

システムとしての速度比較（QGIS vs Canvas）

QGIS 本体の描画と WebGL ベースの Canvas を比較すると、ボトルネックの位置が異なる。比較は「同じデータを同じ忠実度で描く」条件で行う必要がある。

ステージ QGIS 本体 Canvas（WebGL 系）
データ読み出し GDAL/OGR が C++ で直接。GPKG 空間インデックス等で表示範囲だけ読む HTTP フェッチ。形式依存（GeoJSON=全件、FlatGeobuf/PMTiles=Range リクエスト＋空間インデックス）
デコード C++ ネイティブ JS でパース。GeoJSON の全件パースが最大の壁。バイナリ系は軽い
描画対象の選別 空間インデックス＋縮尺抑制＋ジオメトリ簡略化が標準装備 実装依存。MVT/PMTiles は「見えるタイルだけ読む」が構造上強制される
描画本体 QPainter = CPU ラスタライズ（並列化あり・CPU 限界） WebGL = GPU。GPU バッファに乗れば数十万〜百万級でも 60fps 級

比較の結論

  • 描画エンジン単体では Canvas（GPU）が QGIS（CPU ラスタライズ）に対して構造的に速い
  • QGIS が大規模データで粘れるのは描画が速いからではなく「読まない」から。全件 GeoJSON ロードではこの「読まない」に負ける
  • 両者に「範囲外を読まない」仕組み（QGIS=空間インデックス、Canvas=FGB の bbox 参照またはタイル）を持たせれば、同規模で Canvas が常に上回る見通し
  • ラスタ（COG/XYZ）は互角、3D・点群は Canvas 優位、編集・属性表の全件操作は QGIS の守備範囲

実行環境（CDN版・アプリ版・QGIS経由）の描画性能

CDN版（kasugai-canvas-web）もアプリ版（Rust/Axum が web/ を localhost で配信しシステムブラウザを開く）も、描画に使うのは同じ Chromium 系ブラウザ＋同一の web/ 資産であり、描画性能は等しい。 QGIS からの起動（geo_webview）も QDesktopServices.openUrl で既定ブラウザを開くだけであり、QGIS 内に WebView を埋め込んで描画する形態は存在しない。 差が出るのはデータの到達経路のみ。

アプリ版 / QGIS経由（:8089） CDN版
データ経路 localhost サーバがローカルファイルを Range 対応で配信。GB 級の FGB/PMTiles/COG をディスク直結で扱える。QGIS 経由時は geo_webview 内蔵HTTP（:8089）がエンジン＋ /export-data/ を配信 データは HTTPS で到達可能な場所のみ（Pages ホストの DATA/、または LNA 経由の localhost）
制約 特になし（QGIS の :8089 / Canvas の :8510 と直結） GitHub Pages は 1 ファイル 100MB 上限・帯域制限。HTTPS ページから localhost 参照には Local Network Access 許可が必要（アプリ側が /api/browser/lna で登録支援済み）
向く用途 重い業務データ・QGIS 直結の編集・確認 Canvas 未インストール環境への配布・公開（小〜中規模またはタイル化済みデータ）

共通の注意点：リモートデスクトップ等で GPU がソフトウェア描画（SwiftShader 相当）にフォールバックした環境では WebGL が急激に遅くなる。WebGL レンダラの確認を検証手順に含める。

参考：QtWebEngine と WebView2 の速度比較

WebView を埋め込む形態（kasugai の WebView2、将来 geo_webview に QtWebEngine ドックを持たせる場合等）を選ぶ際の比較。いずれも Chromium 系で、WebGL 描画性能は実用上同等。差はレンダリングではなくランタイムの鮮度にある。

QtWebEngine WebView2（kasugai）
エンジン Chromium を Qt に組み込んだフォーク。Qt リリースにバージョン固定され、最新 Chrome より数世代遅れるのが常態 Edge ランタイム（エバーグリーン）。自動更新でほぼ最新 Chromium
WebGL 描画 ANGLE 経由で GPU 加速。描画速度は実用上 WebView2 と同等 同じく ANGLE 経由で GPU 加速
差が出る点 V8/ANGLE が古い分、JS 実行・シェーダ最適化の新しさで劣る。WebGPU 等の新 API・一部コーデックが使えない場合がある 最新最適化が早く降りる。OS 標準ランタイムのため配布物に同梱不要
結論 本用途（CesiumJS/MapLibre の WebGL 描画）では体感差は小さい。選択基準は速度ではなく、Qt 側に UI を統合したいか（QtWebEngine）・OS 標準の最新ランタイムを使いたいか（WebView2）で決める

データ形式のデフォルト方針

ベクター出力の既定形式をデータ規模で階層化する。

規模（目安） 既定形式・経路 備考
小規模（〜5万地物 / 〜30MB） geojson:（全件） 全エンジン対応・QML 再現が最も確実。互換性フォールバックとしても維持
中規模（5万〜30万地物） flatgeobuf:（既定に昇格） 空間インデックス付き単一ファイル。bbox ストリーミング実装を切替の前提条件とする（後述）
大規模（30万〜数百万地物） pmtiles: / mvt: ＋ MapLibre 俯瞰=タイル、詳細ズーム・属性参照=FGB/duckdb: の範囲クエリというハイブリッド。QML の地物単位スタイル再現度は落ちるため属性駆動スタイルで近似
属性集計・フィルタ主体 duckdb: / sql:（bbox=auto 等） クエリは DuckDB-WASM で高速。描画は別途タイル化との併用を検討
3D 建物・点群 3dtiles: 既存経路で可

デフォルト決定

  • 変換を要するベクターの出力先は GeoJSON → FlatGeobuf への切替を既定とする。FGB は ogr2ogr / QgsVectorFileWriter が直接出力でき、ブラウザ側の GeoJSON 正規化で属性が欠落しないため QML 再現度は GeoJSON と同等。ただし現行はブラウザ側で全件 GeoJSON デコードしており効果が限定的なため、bbox ストリーミング実装を切替の前提条件とする
  • 大規模は PMTiles（単一ファイル・Range 対応・静的ホストにそのまま置ける）を第一候補とし、MVT エンドポイント運用も選択肢に残す。CDN 版の 100MB/ファイル制約内では分割を検討
  • 正データ（GPKG/Parquet/FGB/GeoJSON ソース）のネイティブ参照は現行どおり変換しない方針を維持する。上記の既定は「変換を要するベクター」の出力先に適用する

性能面の整備課題（優先順）

  1. flatgeobuf: の bbox/Range ストリーミング化 — 現行 shared/kasc_loader.js は FGB を全件 GeoJSON デコードしており空間インデックスを未活用（最大の課題）。表示範囲の deserialize ＋パン追従に改める
  2. geo_webview 側の pmtiles:/mvt: 行出力と、kasuga_converter での PMTiles/MVT 生成経路（QGIS→タイル自動化）
  3. 大きなベクターデコードの Worker 退避（shared/vector-load.js）でメインスレッドブロックを回避
  4. 実データベンチマーク：同一レイヤを geojson / fgb / pmtiles で出力し、初回描画・パン/ズーム応答・属性参照を計測して階層の閾値を実測で確定
