なぜこのシステムが必要か・誰のためのシステムか

渋谷ミニハッカソンで痛感したのは、多くの現場で GIS が「地図を描くツール」にとどまり、「場と情報を一体化させて理解を支援する基盤」として使われていない点です。KASUGAI Canvas は、本来あるべき GIS の姿を実現することを目指します。

現場の課題（渋谷ミニハッカソンでの課題発掘）

地図情報の伝わりにくさ

「地図情報がどのようなものか、何ができるか」が相手に正しく伝わりにくい。PDF 等の資料では実際の内容が正確に伝わらない。

地図と情報の分断

地図と情報が分断されやすく、地図が資料から孤立した「作り物」として残ってしまう。本来の価値が伝わらない。

空中戦・取り残され

会議等で位置や場所に詳しくない人が取り残され、理解が深まらないまま会議が進む「空中戦」が起きる。

現在の対応とつらい点

段階内容課題
事前の行動説明できる事例をあらかじめ集めるGIS 自体の理解が浅く、何を示せばよいか分からない。実例も手間で作れない
資料化PDF 等にまとめる実際の地図・空間情報の操作性や詳細が正確に伝わりにくい
完成時喜ばれるただし、作るまでに情報の伝達・分断・空中戦が発生しやすい

対象ユーザー：GIS 導入を検討する現場担当者、GIS 専門家ではない会議参加者、位置情報で合意形成したいチーム — 本番導入前に「GIS で何ができて、どんな課題が解決できるか」を体験したい人々です。

一番大事なこと：GIS で「何ができて、何が解決できるか」を先に体験する

結局、最も重要なのは、「GIS を使うことで何ができて、どんな課題が解決できるか」を本番導入前に体験できるかということです。GIS 導入が進まない、あるいは導入されても活用されない現場の多くは、GIS 自体の理解が不足していることが原因です。

そのためのエージェントが、Gemini モデルを使う KASUGAI Canvas のブラウザ内蔵 AI エージェントです。Gemini が function calling で操作するツールを選び、ブラウザ内蔵エージェントがそのツールを実行して GIS を操作します。

  • 体験を先に：本番データを必要とせず、サンプル・資料・GIS が連動した状態で「GIS ならではの理解」を体験
  • 理解を深める：地図と情報の一体化、レイヤーの切り替え、FlyTo・属性表示など、GIS の利点を実感
  • 正しい導入判断へ：体験を通じて「本当に必要なデータ・機能・運用」が見え、無理な導入や失敗を減らす

Gemini エージェント：目標と 3 つの機能

Gemini モデルを使うブラウザ内蔵エージェントの目標は、利用者を正しい GIS 導入判断と課題解決へ導くことです。Gemini が function calling でツールを選び、エージェントが Canvas の GIS API を実行して、以下 3 つの機能を実現します。

自然言語からレイヤーと属性を自動構成

「○○の資料を作って」と話すと、Gemini が必要な地図レイヤー・属性・凡例・カメラ位置を判断し、function calling で選んだツールをブラウザ内蔵エージェントが実行して構成します（実在施設の検索 searchPlaces・URL 指定レイヤー addLayer・生成 GeoJSON の addDataLayer）。

現実に近いサンプルデータを自動生成し、GIS の利点を可視化・体験化

Gemini がエリア・業種・目的に応じた架空サンプルを GeoJSON で生成し、ブラウザ内蔵エージェントが GIS ツールで地図に表示します。本番データがなくても、レイヤー切り替え、FlyTo、属性表示などを通じて GIS ならではの理解を体験できます。

属性から課題を抽出し、平面・内容・解決案を提示した資料作成

Gemini がレイヤー・属性から課題を読み取り、ブラウザ内蔵エージェントが資料作成ツール（showReport）を実行して、平面（地図上の状況）・内容・解決案をまとめた資料のベースを生成します。資料には GIS へのパーマリンクを付与します（buildShareUrl）。

目標：正しい GIS 導入判断と課題解決へ導く

上記 3 つの機能を通じて、利用者は本番導入前に「GIS で何ができて、どんな課題が解決できるか」を体験します。その結果、「本当に必要なデータ・機能・運用」が見え、無理な導入や失敗を減らし、課題解決につながります。

Gemini エージェントの本質：資料を作る・見せる・説明する

Gemini エージェントは、資料の基本である 作る → 見せる → 説明する を自動化するエージェントです。

資料の基本Gemini の機能具体的な動作
作る自然言語からレイヤーと属性を自動構成「○○の資料を作って」と話すだけで、必要なレイヤー・属性・サンプルデータを生成する
見せる現実に近いサンプルデータを自動生成し、GIS の利点を可視化・体験化地図上にサンプルを表示し、レイヤー切り替え・FlyTo・属性表示で GIS 体験を提供する
説明する属性から課題を抽出し、平面・内容・解決案を提示した資料作成属性から課題を読み取り、平面・内容・解決案をまとめた資料を作成する

この 3 ステップを通じて、資料は「PDF への地図貼り付け」ではなく、GIS と連動した生きた理解資料となります。そして、その体験が正しい GIS 導入判断と課題解決へ繋がります。

資料のベース作成と GIS パーマリンク連携

最も重要なのは、資料は資料として必要なものであるという点です。資料は会議の進行、結論の提示、合意形成のための要約として不可欠です。Gemini エージェントは、GIS 上のレイヤー・属性から課題を読み取り、平面（地図上の状況）・内容・解決案をまとめた資料のベースを作成します。

資料に載せきれない背景・範囲・詳細は GIS 側に置き、資料にパーマリンクを載せることで、資料と GIS を双方向に連動させます。

なぜパーマリンクなのか

  • 資料の要約性を維持：資料は簡潔なままで、詳細は GIS へ誘導
  • 深い理解へ誘導：「なぜこの範囲か」「背景データは何か」「周辺の状況は」などを地図上で探索可能に
  • 会議の一体感：参加者全員が同じ URL から GIS を開き、同一視点・レイヤーで議論できる
  • 判断の加速：空中戦を減らし、必要な情報に即座にアクセスすることで、より速い課題解決・意思決定を実現

想定される使い方

  1. 資料の該当部分に ?longitude=...&latitude=...&height=...&pitch=...&heading=... 形式のパーマリンクを配置（buildShareUrl が生成）
  2. 会議参加者がリンクを開くと、KASUGAI Canvas が即座にその場所・視点を表示
  3. 必要に応じてレイヤーを追加・非表示・属性をクリックし、深掘りを行う
  4. 新たな視点が見つかったら、新しいパーマリンクを生成し資料にフィードバック

Gemini との関係

資料作成時に、Gemini モデルが「資料に載せるべき GIS 視点」を判断し、function calling で選んだツールをブラウザ内蔵エージェントが実行して、パーマリンク付き資料と GIS 表示を用意します。資料と GIS がお互いを補完し合うことで、会議の一体感と意思決定のスピードが向上します。

Gemini の狙い

Gemini モデルを使うブラウザ内蔵 AI エージェントは、Gemini の function calling で選ばれたツールを実行し、Canvas の GIS API を通じて上記 3 つの機能を実現します。「正しい GIS 導入判断と課題解決へ導く」ことを目指すエージェントです。「○○の資料を作って」と話すだけで、作る → 見せる → 説明する という資料作成の基本が自動化され、場と情報が一体化した GIS 体験が構築されます。

Gemini の最終目的は、利用者が本番導入前に「GIS で何ができて、どんな課題が解決できるか」を体験し、GIS への理解を深めることにあります。サンプルデータや資料×GIS 連携を通じて、正しい GIS 導入判断と課題解決を後押しします。

プロジェクト説明：KASUGAI Canvas — GIS 利活用を促進する Agentic AI エージェント

KASUGAI Canvas は、ブラウザ上の 3D GIS（CesiumJS）に Gemini API の function calling を組み込んだ Agentic AI エージェント搭載アプリです。ブラウザ内蔵エージェントは Gemini を推論モデルとして使い、自然言語の指示（「○○の資料を作って」等）を受けた Gemini が function calling でチャットツールを選びます。ブラウザ内蔵エージェントがそのツールを実行し、Canvas の GIS API を通じてURL 指定のベクターレイヤー追加・AI 生成サンプル GeoJSON のレイヤー表示・地図移動（FlyTo）・Markdown/HTML 資料の生成とダウンロード・視点パーマリンクの埋め込みまでを一連の流れとして実行します。「GIS が導入前に体験できず、理解されないまま失敗する」という課題に対し、AI がサンプルデータと資料をその場で生成する体験先行型のアプローチで解決します。

バックエンドは Cloud Run（FastAPI）の1サービスに静的配信・/api/gemini（サーバーキー注入のプロキシ）・/api/auth・/api/kasc・/api/data（Cloud Storage への保存）を集約し、同一オリジンで提供します。保存データは V4 署名付き URL でブラウザ⇄Cloud Storage 間を直接転送し、Gemini キーは Secret Manager から注入されるためブラウザに露出しません。本ページに記載する機能はすべて実装済みで、審査用の公開 URL（https://kasugai-canvas-nqh4tuar6a-an.a.run.app/）でそのまま確認できます。

実装済み機能の概要

  • 内蔵AIエージェント（ブラウザ側）：Gemini API の function calling で50種のチャットツールを実行し、「○○の資料を作って」→ レイヤー追加（addLayer/addGeoJsonLayer：URL 指定で .kasc に追記・即時適用）→ サンプル GeoJSON の生成・表示（addDataLayer：AI が生成した GeoJSON オブジェクトを一時レイヤーとして直接表示）→ FlyTo → 資料出力（showReport、Markdown/HTML・ダウンロード可）→ 視点パーマリンク埋め込み（buildShareUrl）→ 飛行ルート生成・再生（addFlyPath→playFlyPath：プレゼン用の自動巡視）まで一連の流れを実行。addLayer/addGeoJsonLayer/applyInspector は外部 http(s) URL を適用前に実在確認し、存在しない URL は拒否。ツール実行の往復上限は既定10で設定画面・AI 指示（setToolMaxSteps）の両方から 1〜20 で変更可、上限到達時はユーザーに継続確認して承認なら延長。生成データには出典・生成時刻・AI生成明記を付与する設計で、実行ツールはチャットに記録される（可観測性）
  • AI プロキシ（キー隠蔽）：POST /api/gemini がサーバーの GEMINI_API_KEY を注入して転送（モデル許可リスト・1MB 上限・レート制限・認証モードで保護）。BYO キー登録済みのブラウザは Gemini を直接呼び、未登録でも /api/capabilities の aiProxy 通知で自動的にサーバーキー経由になるため審査員はキー不要
  • 保存・認証：ID/PASS ログイン（/api/auth）で HMAC トークンを発行し、.kasc と gs:// データを Cloud Storage に保存（/api/kasc・/api/data/<key>、GET は V4 署名付き URL でブラウザ⇄GCS 直接転送）。起動時に同梱 .kasc を冪等シード。審査用 URL は認証モード5で運用中
  • キー・秘匿管理：Gemini・Maps キーと認証情報は Secret Manager 経由で環境変数に注入。Maps キーはブラウザ直接通信に必要なため capabilities で配布し、GCP 側の HTTP リファラ＋API 制限で保護
  • 拡張窓口：外部エージェントプロトコル（{message,project,camera,layers,history,apiKey?} → {reply,actions,report}）により、別実装のエージェントをエンドポイント URL 指定で差し込める

内蔵 AI エージェントの指示文

内蔵 AI エージェントには、モデルに依存しない次の指示を設定します。

あなたは KASUGAI Canvas の GIS 案内エージェントです。
利用者が地図や GIS に詳しくなくても、場所とデータを一緒に見ながら状況を理解し、次の判断につなげられるよう支援してください。

## 目標
利用者の依頼に応じて、Canvas の地図・レイヤー・属性・資料を整え、
「GIS で何が分かり、どんな課題解決に役立つか」を体験できる状態にします。

## 進め方
1. 依頼から対象地域、目的、必要な情報を読み取ります。不明点が結果を大きく左右するときだけ質問します。
2. 実在施設や公開情報が必要なら、検索・既存データを使います。架空サンプルでよい依頼なら、現実の情報と誤認されないサンプルを生成します。
3. 関連するデータを意味の分かる名前のレイヤーに分けて追加し、地図を対象地域へ移動します。
4. 属性や分布から読み取れることを整理します。データだけでは裏付けられないことは事実のように断定しません。
5. 必要なら資料を作成し、地図の状態を再現できるパーマリンクを付けます。
6. 完了時に、追加したレイヤー、分かったこと、サンプルデータか実データか、資料へのリンクを簡潔に説明します。

## サンプルデータの扱い
- 架空データは、名前・説明・資料内に「AI 生成の架空サンプル」と明記します。
- 架空の地点や属性を、実在施設の情報として紹介しません。
- サンプルから導けるのは操作や分析の例までです。現実の意思決定に使える結論として扱いません。
- サンプルを作るときは、依頼された地域・目的に沿った、地図上で比較できるデータにします。

## ツールの使い方
- 依頼を達成するために必要なツールを選び、実行結果を確認してから次へ進みます。
- レイヤー生成は、出力が大きくなりすぎないよう原則1レイヤーずつ行います。
- 同じレイヤーや資料を重複して作らないよう、現在の地図状態を確認します。
- 必要のない設定変更やデータ削除は行いません。
- ツールが失敗した場合は、成功したように装わず、失敗した操作と代替案を説明します。

## 資料の作成
資料には、次の内容を含めます。
- 対象地域と目的
- 地図上で確認できる状況
- データや属性から読み取れる内容
- 課題に対する検討案
- データの出典、または「AI 生成の架空サンプル」である旨
- 地図を開くパーマリンク

検討案は、確認できたデータに基づく案として書き、根拠の限界や追加で必要なデータも必要に応じて示します。

デモシナリオ（3分動画）：渋谷区のまち歩きマップを作る

渋谷区の回遊プランを考えるストーリーです。Gemini に頼むと、公園・文化／観光スポット・飲食店の架空サンプルを各約5件、計約15件の点データとして3レイヤーに作り、地図と案内資料にまとめます。出力を抑えるため、レイヤーは1つずつ順番に生成します。サンプルは実在施設の情報ではないことを明記します。

  1. 依頼：「渋谷区の回遊プランを考えたい。公園、文化・観光スポット、飲食店の架空サンプルをそれぞれ約5件ずつ、別々の点レイヤーにして。サンプルデータであることを明記し、見どころを紹介する資料も作って」と入力します。
  2. 3レイヤーを作成：Gemini が各カテゴリ約5件、合計約15件の架空サンプル地点を GeoJSON で生成し、addDataLayer で「公園」「文化・観光スポット」「飲食店」の点レイヤーを個別に地図へ追加します。各レイヤーに AI 生成サンプルであることを示します。
  3. 地図で見比べる：Gemini が flyTo で渋谷区へ移動。3レイヤーを切り替え、約15件の点の分布や近さを地図上で確かめます。
  4. 案内資料を作成：showReport で各カテゴリの見どころをまとめ、buildShareUrl のパーマリンクを付けます。資料からリンクを開くと同じ地図の視点を再現できることを示して締めくくります。

システムアーキテクチャ図

実線はサーバー経由、破線はブラウザ直接の通信です。Gemini キーは Secret Manager から Cloud Run の環境変数に注入され /api/gemini が転送時に付与するためブラウザには現れません。Maps キーはブラウザの直接通信に使われるため /api/capabilities で配布し、GCP 側の HTTP リファラ制限＋API 制限で保護します。
